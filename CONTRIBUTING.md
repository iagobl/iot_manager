# Project Status

Currently, **external contributions are not accepted**, as the development is part of an individually evaluated academic project.

However, anyone is welcome to:

* Open **issues** to report bugs
* Suggest **improvements or new features**
* Propose **design changes or ideas**

Suggestions will be reviewed to the extent possible.

<br>

# Bug Reporting

If you detect an issue with the system's operation, you can open a **GitHub Issue** including the following information:

* Execution environment (Android, system version, etc.)
* Detailed description of the problem
* Steps to reproduce the error
* Expected result
* Actual result
* Screenshots if possible

This makes it easier to identify and solve the problem more quickly.

<br>

# Code Standards

The project follows a series of development best practices to maintain clear, maintainable, and scalable code.

These include:

* **Feature-based** architecture
* Separation between **presentation, logic, and data access**
* Use of **Row Level Security (RLS)** in Supabase
* Secure management of credentials and sensitive variables
* Consistent naming conventions for files, classes, and methods
* Modular code organization

Whenever possible, priority is given to:

* **Readability**
* **Modularity**
* **Simplicity**
* **Scalability**

<br>

# Commit Convention

The project uses a convention inspired by **Conventional Commits** to maintain a clear history.

Recommended format:

```
<type>: <short description>
```
Example:

```
feat: add device timer functionality
fix: resolve BLE provisioning error
docs: update installation instructions
```

<br>

## Commit Types

| Type         | When to use it                                               |
| ------------ | ------------------------------------------------------------ |
| **feat** | New feature or functionality                                 |
| **fix** | Bug fix                                                      |
| **refactor** | Code restructuring without changing behavior                 |
| **perf** | Performance improvement                                      |
| **docs** | Changes only in documentation                                |
| **build** | Changes in dependencies or build system                      |
| **test** | Adding or modifying tests                                    |
| **chore** | Maintenance tasks (formatting, code cleanup, etc.)           |

### Recommended Rules

* Brief and clear description
* Use **imperative mood**
* Maximum **72 characters** in the title
* One logical change per commit

<br>

# Project Change Process

Although the project is an individual development, the workflow follows common practices in software projects:

1. Create a new branch for each major change
2. Implement the feature or fix
3. Test the functionality
4. Create a commit following the established convention
5. Merge changes into the main branch
